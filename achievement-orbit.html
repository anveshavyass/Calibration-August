Proxy Benchmark Harness

Proves the gateway's enforcement actually works — real attack traffic, replayed through the real policy engine, scored automatically instead of checked by eye. One single command, run_bench.sh, boots the whole system and tests it end to end.

How it works

  • harness.py — loads each case, replays its setup, sends the real test, and tallies the result. Runs all 706 cases and scores itself; nothing gets checked by eye.
  • mock_proxy.py — a stand-in enforcement point. No real proxy existed yet, but the test still had to hit a real policy engine, so this stub checks for an injection phrase and then asks the real OPA for its decision.
  • RequestEvent and Decision — the two schemas both sides speak, kept exactly as they'll be used later. Frozen on purpose, so when the real gateway replaces the mock proxy, it drops straight into this same contract — no rewrite, just a one-line URL change.
  • Scoreboard — every case lands in one of four buckets: attack blocked, attack slipped through, benign correctly allowed, or benign wrongly blocked. It passes only if nothing slipped through and nothing was wrongly blocked.

Dataset

706 cases generated from AgentDojo, not hand-written. AgentDojo is a real, published benchmark built specifically to test prompt-injection attacks against AI agents — it ships real user tasks, real attacker-crafted injection text, and a documented, reproducible way to score whether an agent got compromised.

OPA Input/Output Schema

The frozen wire contract between the gateway and the policy engine — and the tests that keep it from drifting.

Why it's frozen

  • Strictly internal — used only between the gateway and OPA. A caller never sees either; it only ever sees the external RequestEvent and Decision.
  • Frozen ahead of time so features that don't exist yet — like delegated identity claims or real behavioral history — get built to fit inside this shape later, instead of the shape having to change around them.
  • Load-bearing for every consumer of the gateway at once: the policy engine, its own test suite, and every SDK all get built against one exact contract. Change it silently and all of them break together.
  • Enforced automatically, not just by convention: a test suite runs real example inputs through the real policy evaluator and checks the output byte-for-byte against the schema, so the gateway and OPA can never quietly drift out of sync with each other.

opa_input.schema.json

{
  "identity": {
    "agent_svid": "spiffe://poc/agent-banking",   // caller's verified SPIFFE identity
    "delegated_claims": null                      // on-behalf-of user claims — always null, not built yet
  },
  "action": {
    "tool": "send_money",                         // the tool being called
    "args": { "recipient": "...", "amount": 0.01 }, // its arguments
    "sink": "external",                           // where the call is headed
    "capability": "communication.external"        // its resolved capability
  },
  "session_trust": {
    "integrity": "U",                             // T or U — trustworthy or tainted
    "confidentiality": "PUBLIC",                  // PUBLIC, INTERNAL, CONFIDENTIAL, or RESTRICTED
    "first_tainted": "read_file",                 // first source that tainted this session
    "untrusted_sources": {
      "sources": ["read_file"],                   // which sources, capped
      "overflow": false                           // true if more sources than the cap
    },
    "capacity": null                              // bool, enum, string, or null
  },
  "sequence_facts": {}                             // frozen into the shape, stubbed empty until built
}

opa_output.schema.json

{
  "allow": false,                                  // true only if every point below clears
  "deny": ["cannot send tainted data externally"], // all points' reasons merged, untagged
  "points": {
    "authorization": { "allow": true, "deny": [] },        // can this identity call this tool at all
    "taint_egress": { "allow": false, "deny": [           // does tainted data reach an external sink
      "cannot send tainted data externally"
    ] },
    "confidentiality_egress": { "allow": true, "deny": [] } // too-sensitive data leaving, independent of taint
  }

Soak Benchmark CI Test

A dedicated CI job that keeps the policy engine under sustained load and fails the build if latency drifts.

Why this exists

The policy engine has a hard constraint: it can't take longer than 1 millisecond at p99, since every single gateway decision waits on it. Without an automated check, someone would have to manually re-run a load test and eyeball the result before every merge, just to catch a change that quietly pushes latency past that line. This job removes that manual step — it runs the same load test automatically on every pull request, so a latency regression is caught by CI before it ever reaches main, not by a person remembering to check.

Runs on every PR

  • Triggers on every pull request into main, every push to main, and can also be run manually.
  • 3 repetitions of a 10-second, 500 RPS load test against the real authz.rego bundle, 32 concurrent workers, a deterministic traffic mix.
  • Evaluates two things per rep: p99 latency (must stay under 1000µs) and achieved RPS (target 500).

If any rep's p99 goes over 1000µs, that rep is flagged as a build error and the whole job fails — the PR can't merge until it's fixed. If achieved RPS drops below 450, it only warns: the runner may just be slow or noisy that run, not a real regression.

Why it's a separate CI job

  • Runs against the real authz.rego bundle — no mocks in the eval path.
  • Kept apart from unit_test.yaml, because its -race flag distorts latency.
  • Distinct from TestReloadUnderConcurrentLoad, which checks correctness, not speed.

Roadmap — control-plane

Tool Registry & Tool Config

Moving tool and agent configuration off a single JSON file and out of the gateway's source code, into a database that can be edited directly.

Why

  • Every tool's configuration and every agent's permissions currently live in one JSON file — a single change requires loading, parsing, and rewriting the entire file.
  • That file is a single point of failure: one bad edit can affect every tool and every agent, not just the one being changed.
  • The tool registry itself is hardcoded into the gateway's Go source, so adding one tool requires a code change and a full rebuild.
  • This plan replaces both with a database, so tool and agent data can be edited without touching source code.

Build plan

00

Define the two tables

tools — one row per tool: name, sink, capability, data classes, confidentiality. Replaces tools.json. agent_scopes — one row per agent: SPIFFE identity plus allowed capabilities. Replaces data.json's scopes block.

01

Shared plumbing

Postgres (local first, shared later) plus Redis. One shared database-connection helper for both tables.

02

Tool registry pipeline

CRUD API on tools, Redis-cached. A background job hot-swaps the gateway's in-memory tool map — same pattern as OPA's hot reload. Stays on the Go side; never touches OPA.

03

Tool configuration pipeline

CRUD API on agent_scopes, Redis-cached. A background job converts it to OPA's data.json shape. Full reload for simplicity, or patch one agent once past prototyping.

04

Failure handling

Redis down: serve the last good copy, no fresh updates. No data at boot: refuse to start, loudly — same as a missing tools.json today.

05

Verification

Unit tests for every CRUD operation. One live test per pipeline: a database change shows up in an actual decision.

SmartDoc — Document Q&A Assistant

Turn a library of PDF documents into a grounded, cited Q&A assistant — ask in plain English, get answers sourced back to the exact file, page, and paragraph.

Backend Frontend Vector DB History LLM Tests

Why it exists

Hand-searching PDF policies and manuals is slow, and pasting a whole document into a chatbot invites the model to guess when the document doesn't actually cover the question. SmartDoc retrieves only the passages relevant to a question, forces the LLM to answer from those passages alone, and cites exactly where each answer came from.

What it does

  • Ingests PDFs — chunks, embeds, and stores them in a vector database.
  • Retrieves only the top-5 relevant chunks per question.
  • Says "not covered" instead of guessing when nothing's relevant.
  • Answers only from retrieved excerpts, with a cited source.
  • Remembers conversations — reopen or delete anytime.

Core concepts

  • Chunking — split into small overlapping pieces so each embedding stays focused.
  • Embeddings — text turned into vectors; similar meaning sits close together.
  • Retrieval — top-5 closest chunks pulled by similarity.
  • Relevance gate — skips the LLM entirely if nothing's actually relevant.
  • Grounded answering — the LLM never answers beyond what was retrieved.
  • Citation margin — only chunks near the best match get cited.
  • Follow-up resolution — rewrites context-dependent questions before retrieval.

Testing

  • Source — 5 synthetic PDFs for a fictional company ("Clearwave Technologies"), generated (not hand-written) so the facts inside are consistent and known in advance — good material for demoing citations and testing retrieval.
  • Documents — 2 HR policies, a product manual, an onboarding guide, and an SOP, covering exactly the document types this project targets. Regenerate or edit them anytime.

Also tested against 3 real internal documents — Calfus policies pulled from GreytHR — which ingested cleanly and answered questions as expected, confirming the pipeline works beyond the synthetic sample set.

Novelty features

  • Multi-document scoping — ask across all docs, one, or several; multi-doc scope answers independently per document instead of pooling chunks into one search.
  • Conversational follow-ups — recent chat history resolves context-dependent questions before retrieval even runs.
  • Two hallucination guards — a similarity threshold blocks the LLM call outright, and the LLM itself flags insufficient context after reading.
  • Paragraph-level citation — file, page, and paragraph, with the exact supporting sentence highlighted inside the excerpt.
  • Summarization as its own intent — whole-document summary requests are detected and routed separately from cited Q&A.
  • Persistent multi-conversation history — full session CRUD backed by SQLite, surviving restarts.
